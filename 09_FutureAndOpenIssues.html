Shado Guesser 基本設計書

09：将来拡張・残課題

本設計書では、 Shado Guesser初期版では実装しない機能、 将来的に追加を検討する機能、 および将来機能追加時にも維持すべき 基本設計原則を整理する。

本書に記載された将来機能は、 明示的に「実装予定」とされたものを除き、 実装を保証するものではない。

1. 本書の位置づけ

01～08では、 Shado Guesser初期版を実装するために必要な 基本仕様を定義した。

09では、 初期実装に必要のない機能を無理に組み込まず、 将来追加できる可能性だけを整理する。

将来機能のために 初期版の実装を過度に複雑化しない。

2. 将来機能の分類

分類 意味
優先度高 初期版完成後、比較的優先して検討する機能
将来候補 必要性が出た場合に検討する機能
初期版対象外 現在は実装しないことが確定している機能
調査項目 実際のデータや運用開始後に判断するもの

3. 優先度の考え方

将来機能の優先度は、 ゲーム体験への効果、 実装コスト、 運営負荷、 既存設計への影響を考慮して決定する。

4. 優先度高：ランダムマッチ

ランダムマッチ機能は、 初期版完成後の将来対応候補の中で 優先度を高めに設定する。

ルームIDを知人へ共有する通常Battleとは別に、 対戦相手を自動的に探してBattleを開始できる機能を追加する。

8. マッチング待機中のVersion変更

Current Version変更によって 待機開始時のVersionがCurrentではなくなった場合は、 古い条件の待機Ticketをそのまま新規マッチへ使用しない。

実装時には、 待機Ticketを無効化して再参加させる、 または新Current Version条件へ再登録する等、 Version混在を防ぐ処理を行う。

  • 対応Search Indexとの整合。
  • ロールバック対象として必要ない。
  • Source Archiveとの追跡関係。

54. 将来機能追加時の共通原則

将来機能を追加する場合でも、 01～08で確定した以下の基本原則を維持する。

  • サーバーをゲーム状態のSource of Truthとする。
  • 正解カードをゲーム終了前にクライアントへ公開しない。
  • 正式判定をサーバー側で行う。
  • ゲーム開始時のData Versionを固定する。
  • Published Versionを書き換えない。
  • 未知データを推測しない。
  • 公式構造化Source Dataを正式データソースとする。
  • AIを正式カードデータソースにしない。
  • 進行中ゲームをCurrent Version変更で変化させない。

55. API互換性

56. Data Version互換性

将来カードデータ構造を拡張しても、 既存Published Versionを 新構造へ自動上書きしない。

57. ゲームルール変更

将来ゲームルール自体を変更する場合は、 既存設計書の該当仕様を 正式に改訂してから実装する。

運営画面の設定値だけで 設計書と異なるゲームへ変化させない。

58. 将来機能とセキュリティ

利便性のために 秘密情報をクライアントへ移す設計変更を行わない。

特に以下は維持する。

  • sessionTokenを秘密として扱う。
  • reconnectTokenを秘密として扱う。
  • 管理APIを認証する。
  • 正解をクライアントへ保持しない。

60. 将来機能とWebSocket

リアルタイム通信が必要な機能のみ WebSocketを使用する。

64. 残課題：公式Source Mapping

以下は設計未確定ではなく、 初回Importer実装時に 公式データから確認する調査項目である。

  • Source type IDの正式な意味。
  • rarity IDの正式名称。
  • tribe IDの正式名称。
  • 「全て」に相当する公式表現。
  • card_set_idと正式パック名。
  • release_order。
  • 画像参照方式。
  • Keyword構造化データの有無。

65. Mapping調査は仕様変更ではない

上記のID対応が未確認でも、 「未知ならImportを止める」 という08の設計自体は確定済みとする。

66. 残課題：実運用後の負荷確認

実際の利用者数が判明した後、 必要に応じて以下を確認する。

  • 同時Battle数。
  • WebSocket接続数。
  • D1アクセス量。
  • Search Indexサイズ。
  • Source Archive容量。
  • エラーログ増加量。

これらは初期設計を変更する前提ではなく、 実測後の最適化項目とする。

67. 残課題：レート制限

APIへの具体的なRate Limit値は、 実運用・アクセス量を確認して調整する。

Rate Limitの存在自体は想定するが、 具体値は初期実装時または運用開始後に調整可能とする。

68. 残課題：Matchmaking規模

ランダムマッチ実装時には、 実際の同時待機人数を考慮して Matchmaking Stateの実装方法を決定する。

ローテーション固定というゲーム仕様は確定し、 待機キューの内部実装方式のみ将来決定する。

77. 最終方針

初期版では機能を必要以上に増やさず、 01～08で定義したゲームを 安定して動作させることを優先する。

その後、 利用状況や必要性を確認しながら ランダムマッチをはじめとする 将来機能を段階的に追加する。

特にランダムマッチについては、 「ローテーション固定・ログイン不要・レートなし・ 成立後は既存Battleへ移行」 というシンプルな構成を基本案として保持する。
