Shado Guesser 基本設計書

03：判定仕様

本設計書では、Shado Guesserにおける 正解カードと回答カードの比較方法、 一致・部分一致・不一致、 数値の大小判定、 タイプ・キーワード能力の集合判定、 特殊値「全て」、 および判定不能なデータ異常発生時の処理を定義する。

1. 判定の基本方針

プレイヤーがカードを回答した場合、 サーバーは回答カードと正解カードの Normalized Dataを比較し、 各項目ごとの判定結果を生成する。

生成された判定結果をブラウザへ返し、 画面側で色・矢印等を表示する。

    ↓

2. 正式な判定元

正式な回答判定は サーバー側 で行う。

  • ブラウザ側の判定結果を正式な値として信用しない。
  • 正解カードはサーバー側で保持する。
  • 回答card_idをサーバー側で検証する。
  • 回答可能範囲をサーバー側でも検証する。
  • 正式な判定結果はサーバーが生成する。
  • ゲーム開始時に固定されたdata_version_idのデータを使用する。

3. ゲームそのものの正解判定

ゲームの「正解」は、 回答カードIDと正解カードIDが一致した場合のみ成立する。 

guessedCardId === answerCardId

の場合のみ正解とする。

guessedCardId、 answerCardId はゲーム状態上の概念名であり、 カードを識別する元のIDは card_id である。

各判定項目が偶然すべて一致している別カードが存在しても、 card_idが異なる場合は正解とはしない。

4. 項目判定とゲーム正解判定の分離

「カードパックが一致」 「コストが一致」 「タイプが一致」 等の項目判定と、 ゲームそのものの正解判定は別処理とする。 

各項目

カードパック：一致
クラス：一致
レアリティ：一致
分類：一致
タイプ：一致
コスト：一致
攻撃力：一致
体力：一致
キーワード：一致

でも

guessedCardId !== answerCardId

↓

ゲームとしては不正解

6. 黄色を使用する項目

黄色の部分一致判定を使用するのは、 複数値を持ちうる以下の項目のみとする。

  • タイプ。
  • キーワード能力。

カードパック・クラス・レアリティ・分類等の 単一値項目では黄色を使用しない。

7. 単一値項目

以下の項目は、 原則として1つの判定値を持つものとして比較する。

  • カードパック。
  • クラス。
  • レアリティ。
  • 分類。
回答値 === 正解値
→ 緑

回答値 !== 正解値
→ 灰色

12. 数値判定

数値として大小関係を比較する項目では、 回答値と正解値の関係に応じて ▲・▼を表示する。

回答値 > 正解値

回答値 === 正解値

17. 攻撃力・体力の特殊ルール

攻撃力 atk および体力 life は、 フォロワーカードでのみ ゲーム上意味を持つ数値として扱う。

回答カードと正解カードの両方がフォロワーの場合のみ atk / lifeを数値比較する。

公式Source Dataで、 スペル・アミュレット等の atk / lifeに0が存在する場合でも、 Shado GuesserのNormalized Dataでは 非フォロワーのatk / lifeを NULL として扱う。

21. タイプ判定

画面上の「タイプ」は、 04 データ設計で定義する tribes および card_tribes を基準として判定する。

タイプはカードによって複数の値を持つ可能性があるため、 単一値ではなく集合として比較する。

画面上の 「分類」 と 「タイプ」 は別項目である。 

画面「分類」
→ Normalized Dataの type
→ フォロワー / スペル / アミュレット


画面「タイプ」
→ tribes / card_tribes
→ 宴楽 / 兵士 / 学園 等

完全一致
→ 緑

一部でも共通タイプあり
→ 黄色

共通タイプなし
→ 灰色

26. タイプ「全て」

一部カードでは、 タイプとして特殊な状態 「全て」 を持つ場合がある。

「全て」は単なる通常タイプIDではなく、 すべての通常タイプと意味上重複する 特殊なタイプ状態として扱う。

04 データ設計で定義する 

tribe_mode = all

を使用する。

「全て」を、 現在存在するすべてのtribe IDへ展開して保存しない。

通常タイプ集合と tribe_mode を使用して以下の順序で判定する。

2.

AND

3.

→ miss


4.

双方 normal

6.
その他

36. タイプ・キーワードの判定単位

タイプ・キーワード能力については、 個々の文字や各要素を別々に色分けするのではなく、 項目全体として1つの判定状態を返す。 

タイプ：

宴楽・兵士

↓

部分一致なら

項目全体を黄色

「宴楽だけ緑、兵士だけ灰色」のような 要素単位の色分けは基本仕様としない。

37. 能力・効果テキスト

カードの能力・効果テキストは プレイヤーへ情報として表示する。

能力・効果テキストは判定しない。
  • 緑判定なし。
  • 黄色判定なし。
  • 灰色判定なし。
  • 正解判定には使用しない。

38. 判定結果の基本構造

サーバーからブラウザへ返す判定結果は、 各UI項目が判別可能な構造とする。 

概念例：

{
    pack: "match",
    class: "miss",
    rarity: "match",
    classification: "match",
    tribes: "partial",
    cost: "higher",
    atk: "lower",
    life: "match",
    keywords: "partial"
}

カードデータの正式名称に合わせ、 攻撃力・体力は atk / life を使用する。

画面上の「タイプ」は データ上の tribes と混同しない構造にする。

APIレスポンス全体の具体的なJSON形式は 06 サーバー・Cloudflare設計で定義する。

41. 全ゲームモードで共通判定

カード比較ルールは、 ゲームモードによって変更しない。

モード 判定ルール
ソロ 共通
デイリー 共通
2人出題 共通
2人対戦 共通

42. 時間切れランダム回答

2人対戦の時間切れにより サーバーがランダム回答を生成した場合も、 通常回答と同じ判定ロジックを使用する。

時間切れ専用の別判定方式は設けない。

02で定義したとおり、 時間切れランダム回答の候補から 正解カード自体は除外される。

43. データ検証

判定処理を開始する前に、 正しい判定を行うために必要な Normalized Dataが正常に存在することを確認する。

データが異常な場合に、 推測や暫定値で判定を続行しない。

44. 正常な「値なし」とデータ異常の区別

カード仕様上、 値が存在しないことが正常な項目と、 本来必要な値が欠損している異常状態を区別する。

例 扱い
スペルのatkがNULL 正常。比較対象外「－」
アミュレットのlifeがNULL 正常。比較対象外「－」
タイプを持たないカード 正常。「－」
キーワード能力を持たないカード 正常。「－」
フォロワーなのにatkがNULL 異常
フォロワーなのにlifeがNULL 異常
存在しないclassを参照 異常
存在しないcard_set_idを参照 異常
未知のNormalized type 異常

45. 判定不能となるデータ異常

以下のような状態により正常な比較ができない場合、 判定を中止する。

  • 必要なカードデータが存在しない。
  • 必須項目が欠損している。
  • 必須項目が不正な型になっている。
  • 存在しないクラス・カードセット等を参照している。
  • フォロワーのatk / lifeを取得できない。
  • 正解カードデータを取得できない。
  • 回答カードデータを取得できない。
  • 固定data_version_idのデータを取得できない。
  • 判定ロジックが正常に処理を完了できない。

46. データ異常時の基本処理

データ異常検出

↓

回答判定を中止

↓

正常なGuessとして確定しない

↓

ゲームを正常状態として続行しない

↓

ゲームをerror状態へ

↓

一意のエラーIDを生成

↓

サーバーへエラーログ保存

↓

ユーザーへ安全なエラー画面表示

異常値を 0・空文字・空配列・既定値・AI推測値等へ置き換えて ゲームを続行しない。

47. データ異常時の回答扱い

正常な判定を完了できなかった回答を、 通常の成功したGuessとして扱わない。

  • 正常な判定結果として履歴へ追加しない。
  • 誤った比較結果を表示しない。
  • 通常の不正解として回答回数だけ消費しない。
  • 通常の勝利・敗北・失敗として処理しない。
  • ゲームをerror状態へ移行する。

回答状態更新と判定処理をどの単位で 原子的に確定するかは 06 サーバー・Cloudflare設計で定義する。

48. エラーのサーバーログ保存

判定不能なデータ異常が発生した場合、 運営側で原因を追跡できるよう サーバー側へ詳細なエラーログを保存する。

各エラーには 一意の エラーID を付与する。

49. エラーログ項目

サーバー側の詳細ログでは、 原因調査に必要な情報を記録できる構造とする。 

概念例：

error_id
error_code
timestamp

game_mode
game_id
room_id

answer_card_id
guessed_card_id

invalid_field
invalid_value

data_version_id
version_code

request_id

stack_trace

ログへCookie・Authorization・CSRF Token等の 不要な認証・セッション秘密情報を保存しない。

実際に保存する項目は エラー種別に応じて必要なものを記録する。

ログの具体的なテーブル構造は 04・06・07の設計へ従う。

50. エラーID

ユーザーからの問い合わせ内容と サーバーログを対応付けるため、 エラー発生ごとに一意のエラーIDを発行する。 

SG-20260728-A8F3K2

同一エラーIDから 運営側が対応する詳細ログを検索できるようにする。

51. エラーコード

原因の大分類を識別するため、 エラーコードを持たせる。

エラーコード例 意味
CARD_DATA_INVALID カードデータの値が不正
CARD_DATA_MISSING 必要なカードデータが欠損
CARD_REFERENCE_ERROR クラス・カードセット等の参照先が不正
JUDGEMENT_ERROR カード判定処理中の異常
GAME_STATE_ERROR ゲーム状態の不整合
DATABASE_ERROR 必要データの取得失敗等

エラーコードは実装上必要になった場合に追加可能とする。

52. ユーザー向けエラー画面

データ不具合によってゲームを正常に継続できない場合は、 安全な情報のみを使用したエラー画面を表示する。

  • その他セキュリティ上公開すべきでない情報。

エラー画面内の 「お問い合わせ」 は、 サイトのお問い合わせページへのリンクとする。

お問い合わせページは 新しいタブ で開く。 

<a
    href="contactUrl"
    target="_blank"
    rel="noopener noreferrer"
>
    お問い合わせ
</a>

56. お問い合わせURLの管理

お問い合わせページURLは、 ゲームコードの複数箇所へ直接書き込まず 設定値として管理する。 

SG_CONFIG.contactUrl

独立サイトからWordPress等へ移設して お問い合わせページURLが変更された場合も、 設定変更だけで対応可能な構造とする。

57. 判定エラーと通常の不一致

ゲーム上の「不一致」と システム上の「判定不能エラー」は 明確に分離する。

状態 処理
クラスが違う 正常な灰色判定
コストが違う 正常な▲ / ▼判定
タイプが違う 正常な灰色判定
必要データが壊れている エラー
存在しない参照ID エラー
Followerのatk / life欠損 エラー

58. 偽の既定値を使用しない

データが取得できない場合に 以下のような処理を行わない。 

atkがない
→ 0として判定

lifeがない
→ 0として判定

classがない
→ Neutralとして判定

tribesがない理由が不明
→ 空集合として判定

card_set不明
→ トークン扱い

正常な「値なし」であることが データモデル上確定している場合のみ、 NULL・空集合等を正常値として扱う。

59. データバージョン

どのカードデータを使用して判定したか追跡できるよう、 ゲーム開始時に data_version_id を固定する。 

data_version_id

→ D1内部で使用するVersion識別子


version_code

→ 人間向けVersion表記
→ 例：2026-07-28-01

ゲーム開始時点の data_version_id をゲーム終了まで維持する。

60. カードデータ更新中のゲーム

進行中ゲームの途中で Current Versionが変更された場合も、 途中から新しいデータへ切り替えない。 

ゲーム開始

data_version_id = A

↓

CurrentがBへ変更

↓

進行中ゲーム
→ Aを維持

新規ゲーム
→ Bを使用

Dailyについては、 Current変更時に当日のDailyを停止する 07の専用ルールが別途適用される。

これはカード判定ロジックが途中でVersion Bへ切り替わることを意味しない。

62. 回答対象範囲の検証

サジェストUIで対象外カードを表示しないだけでなく、 サーバー側でも回答カードが 現在のゲーム対象範囲内か確認する。

対象外card_idが直接送信された場合、 正常な回答として受理しない。

クライアント側の対象範囲判定はUI補助であり、 正式な回答可否判定ではない。

63. 色そのものと判定ロジック

サーバーは 「緑色そのもの」を返すのではなく、 意味上の判定状態を返す。 

サーバー：

match
partial
miss
higher
lower
notApplicable


↓

ブラウザ：


match
→ 緑

partial
→ 黄色

miss
→ 灰色

higher
→ ▲

lower
→ ▼

notApplicable
→ －

これにより、 将来デザイン上の色を変更しても 判定ロジックそのものを変更する必要がない。
