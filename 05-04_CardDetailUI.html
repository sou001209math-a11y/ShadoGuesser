Shado Guesser 基本設計書

05-04：カード詳細UI

本設計書では、 Shado Guesserの回答履歴カードを展開した際に表示する カード詳細情報の構成、 項目順、 列構成、 ラベル表示、 カードデータとの対応、 長文・複数値の扱いについて定義する。

カードデータの正式な内部構造は 「04 データ設計」、 カード属性の正式な判定方法は 「03 判定仕様」に従う。

1. 目的

カード詳細UIは、 プレイヤーが回答したカードの情報と サーバーから返された判定結果を確認し、 次の回答を考えるための主要な情報表示領域である。

一度に多数の項目を扱うため、 横長の巨大テーブルではなく、 スマートフォンでも確認しやすい カード型・複数段レイアウト を採用する。

各回答で同じ位置に同じ項目を表示し、 複数の回答を比較しやすい構造とする。

基本方針
  • 履歴カードを展開した場合のみ詳細を表示する。
  • 横長の巨大テーブル形式にはしない。
  • 項目の並び順を固定する。
  • 項目名は値の上へ小さく表示する。
  • 長い文字列は自然に折り返す。
  • PC・スマートフォンで情報順序を可能な限り統一する。
  • 画面表示名と内部データ名を分離する。
  • 正式な判定状態はサーバーから受け取った値を使用する。

7. カードパック

カードパックは詳細UIの最上段へ 1列で表示する。

  • 長い場合は自然に折り返す。
  • 原則「…」で省略しない。

8. カードパック表示名

カードパック欄の表示名は、 04で定義したDerived Ruleに従う。 

if (is_token === true) {

    pack_name = "トークン";

}
else if (card_set_id === 10000) {

    pack_name = "ベーシック";

}
else {

    pack_name = card_sets.name;

}
カード状態 画面表示
is_token = true トークン
is_token = false
card_set_id = 10000		 ベーシック
その他の通常カード card_sets.name

Tokenについて、 card_set_idから通常カードパックへの所属を推測して表示しない。

card_set_idの数値から 「第○弾」等を推測しない。

27. 能力テキスト

Keyword欄の下へ skill_text 全文を表示する。 

┌────────────────────────────────────────────┐
│ ファンファーレ ～～する。                  │
│                                            │
│ 進化時 ～～する。                          │
└────────────────────────────────────────────┘
  • skill_text全文を表示する。
  • 元データの改行を可能な限り維持する。
  • 表示用情報として扱う。
  • 能力文章そのものは判定しない。

28. skill_textの保存単位

能力テキストは skill_text という1つのTEXTとして扱う。

  • ファンファーレごとの専用列を作らない。
  • 進化時能力ごとの専用列を作らない。
  • 表示時も1つの能力本文として扱う。

29. 能力テキストの見出し

以下の専用見出しは表示しない。 

効果

Effect

能力
表示： 
ファンファーレ ～～する。
進化時 ～～する。

30. 能力テキストの全文表示

  • 文字数による切り捨てを行わない。
  • 「続きを読む」を基本的に設置しない。
  • 「…」で能力文を省略しない。
  • 自然に複数行へ折り返す。
  • テキスト量に応じてカード高さを伸ばす。

31. 能力テキストは判定しない

  • 文章一致判定なし。
  • 緑・黄色・灰色を付けない。
  • ▲・▼を付けない。
  • ゲーム正解判定へ使用しない。

36. レイアウトの安定性

  • 回答カードによって項目位置を変更しない。
  • Follower / Spell / Amuletでも同じ基本構造。
  • atk / life対象外でも列を消さない。
  • 対象外は「－」。
  • 回答同士を縦方向に比較しやすくする。

39. 長い文字列

  • カードパック名は折り返す。
  • タイプは折り返す。
  • Keywordは折り返す。
  • skill_textは折り返す。
  • 横スクロールを基本的に発生させない。
  • 必要に応じてカード高さを伸ばす。

43. Data Version

カード詳細に使用するカード情報は、 ゲーム開始時に固定された data_version_id に属するNormalized Dataを使用する。 

Game Start

data_version_id = A
version_code = A


↓

Current VersionがBへ変更


↓

進行中Game

data_version_id = Aを継続

カード名・パック名・class・rarity・type・tribes・ cost・atk・life・keywords・skill_text・image_refを ゲーム途中から新Versionへ切り替えない。

44. data_version_idとversion_code

data_version_id

→ Server / D1内部のVersion識別子


version_code

→ 人間向けVersion表記
→ 例：2026-07-28-01

dataVersion という曖昧な名称は原則使用しない。

45. Current変更時

通常の開始済みゲームでは、 Current変更によってカード詳細情報を差し替えない。

Dailyについては、 Current変更により当日のDaily自体が停止する 07の専用仕様が適用される。

これは進行中Dailyのカード詳細だけを 新Versionへ切り替えるという意味ではない。

46. 正解カードの詳細表示

ゲーム進行中に 正解カードのカード詳細をBrowserへ送信・表示しない。

正解カードの情報は、 通常のゲーム終了後に 05-07のResult Screenで表示可能となる。

Daily停止等、 正解を公開しない終了状態では表示しない。

47. 回答カードの情報

回答履歴へ追加されたカードについては、 正常に成立したGuessに対する サーバー確定済み情報を表示する。

  • Clientだけで判定状態を生成しない。
  • Serverからの正式Stateを使用する。
  • Reload / Reconnect後もServer Snapshotから復元する。

48. stateVersionとの関係

リアルタイムゲーム等で Server Stateに stateVersion が存在する場合、 古いSnapshotでカード詳細・履歴を巻き戻さない。

↓

↓

反映しない

54. カード詳細UIで行わないこと

  • 詳細部分でカード画像を再表示しない。
  • 詳細部分でカード名を再表示しない。
  • skill_textを判定しない。
  • 長文を強制省略しない。
  • タイプを1件ずつ縦に分割しない。
  • Keyword欄へ横Scrollを作らない。
  • 非Followerのatk/lifeを0として表示しない。
  • 進化後atk/lifeを初期版Guess判定に使用しない。
  • 回答カードごとに項目順を変更しない。
  • データ異常を「－」で隠さない。
  • Tokenをtype=4等として分類欄へ表示しない。
  • Source raw typeをClient側で直接Mappingしない。
  • card_set_idからPack名を推測しない。
  • Clientだけで正式判定を再計算しない。
  • ゲーム途中でCurrent Versionのデータへ切り替えない。
