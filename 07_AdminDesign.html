Shado Guesser 基本設計書

07：管理画面・運営操作

本設計書では、Shado Guesserの運営者が使用する管理画面について、 認証、Dashboard、カードデータ閲覧、Data Version管理、 Daily管理、エラーログ、メンテナンス、 運営設定、監査ログ、および管理APIの安全性を定義する。

管理画面は一般プレイヤー向けゲーム画面とは完全に分離し、 管理者のみがアクセス可能な非公開領域として運用する。

1. 目的

管理画面の目的は、 カードデータやゲームロジックそのものを自由に編集することではなく、 Shado Guesserを安全に運営するために必要な 状態確認・Version公開・Daily停止・障害確認等を行うことである。

基本方針
  • 一般ユーザーから管理画面へアクセスできないようにする。
  • 初期版では管理者権限を1種類のみとする。
  • カードデータを管理画面から直接編集しない。
  • Published Versionは書き換えない。
  • Data Versionの公開・Current変更は管理画面から可能。
  • Daily正解を途中変更しない。
  • 問題があるDailyはその日自体を停止する。
  • ゲームルールの基本数値を管理画面から変更しない。
  • 重要な管理操作は監査ログへ残す。
  • メンテナンスモードを用意する。

3. 一般ゲーム画面との分離

管理画面は一般プレイヤー向けの Shado Guesserゲーム画面とは分離する。 

一般ユーザー

https://game.example.com/


管理者

https://admin.example.com/

実際の本番ドメイン名は実装時に決定する。

専用サブドメインではなく /admin/ 配下で構成することも可能だが、 一般公開画面と管理画面を明確に分離できる構成を優先する。

4. 管理画面認証

初期版ではShado Guesser独自の 管理者ID・パスワード機能を作成しない。

Cloudflare Access等を利用し、 管理画面自体を認証済み管理者のみアクセス可能にする。

5. 管理者アカウントテーブル

初期版ではShado Guesser内に 以下のような独自アカウントテーブルを作成しない。 

admins

admin_passwords

admin_sessions

管理者認証は外部の認証保護を利用し、 ゲームDBへ独自パスワードを保存しない。

6. 管理者権限

初期版では管理権限を細かく分けない。

権限 初期版
閲覧専用管理者 作らない
データ管理者 分離しない
Daily管理者 分離しない
システム管理者 分離しない
管理者 1種類

将来複数人運営となり、 権限分離が必要になった場合は拡張可能とする。

34. Daily事前生成

初期版では管理画面からDailyを事前生成しない。

06で定義した 「その日の最初のアクセス時に自動生成」 を維持する。

Daily運用を単純化し、 事前生成後のカード更新・Version変更等による 管理の複雑化を避ける。

35. Daily正解の確認

Dailyが生成済みの場合、 管理者は正解カードを確認可能とする。

一般ユーザー向けAPI・HTMLには 正解情報を公開しない。

36. Daily正解の変更

生成済みDailyの正解は変更しない。

以下の機能は作成しない。

  • 正解変更。
  • 正解再抽選。
  • Daily Revision。
  • 代替問題への切替。
  • 緊急正解変更。

37. Dailyに問題が発生した場合

状態変更操作は POST等の明示的な変更リクエストとして実装する。

90. CSRF等への対策

管理APIはブラウザ認証を伴うため、 管理者が意図しない外部サイトから 変更要求を実行されないようにする。

  • Access認証確認。
  • 同一Originを基本とする。
  • Origin等の検証。
  • 状態変更APIにCSRF対策を適用。
  • GETで変更処理を行わない。

91. 管理画面のキャッシュ

管理画面の状態・エラーログ・Daily情報等を 一般CDNキャッシュへ長時間残さない。 

Cache-Control: no-store

92. 管理画面からゲームDOを直接編集しない

初期版では、 進行中ゲームの内部状態を管理画面から 書き換える機能を作成しない。

  • 回答回数を増減しない。
  • 正解カードを変更しない。
  • Battle勝敗を変更しない。
  • 手番を強制変更しない。
  • 履歴を削除しない。

93. 進行中ゲーム一覧

初期版では 全進行中ゲームを管理画面へ一覧表示する機能を必須としない。

障害調査で必要となった場合は、 gameId / roomId指定による状態確認機能を 将来的に追加可能とする。

94. 管理画面と秘密情報

管理画面にも以下の秘密情報を表示しない。

  • sessionToken。
  • reconnectToken。
  • API Secret。
  • Cloudflare Secret。
  • 秘密鍵。

95. HTMLへ秘密情報を埋め込まない

禁止：

<script>

const ADMIN_SECRET = "...";

</script>

管理権限は クライアントJavaScript内の秘密値で保護しない。

96. 管理画面のレスポンシブ

管理画面もPC・スマートフォンで閲覧可能とする。

ただしカードVersion公開等の重要運営操作は PC利用を主用途として設計してよい。

97. モバイルでの誤操作防止

  • 重要ボタンを小さく配置しない。
  • Current変更等をワンタップ確定しない。
  • 確認モーダルを必須とする。
  • 隣接する危険操作を密集させない。

98. 管理画面のCSS

112. 管理操作失敗時

管理操作の通信が失敗した場合、 クライアントだけで成功したことにしない。

  • サーバー状態を再取得する。
  • requestIdで処理済みか確認可能とする。
  • 成功していなければ再試行可能とする。

113. Current切替失敗時

Current Versionだけ変わった、 Daily停止だけ行われた、 監査ログだけ残った、 といった不整合を可能な限り発生させない。

関連するD1更新を同じ管理処理単位として扱う。
