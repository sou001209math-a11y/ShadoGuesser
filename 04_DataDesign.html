Shado Guesser 基本設計書

04：データ設計

本設計書では、 Shado Guesserで使用するカードマスターデータ、 各種マスター、 カードデータVersion、 検索用静的データ、 Dailyデータ、 運営設定、 監査ログ、 エラーログ等の 永続データ構造を定義する。

進行中ゲームの状態管理、 Durable Objects、 WebSocket、 再接続、 deadline等については 「06 サーバー・Cloudflare設計」で定義する。

カードデータの取得・Importer・Mapping・Validation・ Diff Report・Publish手順については 「08 データ更新手順」で定義する。

1. データストア

Shado Guesserの主要な永続データストアには Cloudflare D1 を使用する。

D1で管理する主なデータ
  • カードデータVersion。
  • カードマスター。
  • カードセットマスター。
  • クラスマスター。
  • 分類マスター。
  • レアリティマスター。
  • タイプマスター。
  • カードとタイプの関連。
  • キーワード能力マスター。
  • カードとキーワード能力の関連。
  • Daily問題データ。
  • Daily提供状態。
  • 運営設定。
  • エラーログ。
  • 管理操作監査ログ。

2. D1へ保存しないデータ

すべてのゲームデータをD1へ保存するわけではない。

進行中ゲームの一時状態は Durable Objectsを使用する。

データ 担当
カードマスター D1
Data Version D1
Daily共通データ D1
運営設定 D1
監査ログ D1
エラーログ D1
Solo進行状態 GameSessionDO
Daily個人進行状態 GameSessionDO
2人出題進行状態 ChallengeGameDO
2人対戦進行状態 BattleRoomDO

3. 基本方針

  • 公式カード情報と同じ意味の項目名は可能な限り維持する。
  • Source DataとNormalized Dataを分離する。
  • カードの正式識別にはカード名ではなく card_id を使用する。
  • 表示名称と内部IDを分離する。
  • ゲーム判定に必要な情報を構造化する。
  • 能力テキストは全文をTEXTとして保持する。
  • カード画像BinaryをD1へ保存しない。
  • Data Versionごとの完全Snapshotを基本とする。
  • Published Versionを書き換えない。
  • 進行中ゲームは開始時のdata_version_idを使用し続ける。
  • 未知値を推測して正常データへ変換しない。

12. Current Version

新規ゲームが使用するPublished Versionを Current Versionとする。

  • CurrentにできるのはPublished Versionのみ。
  • DraftをCurrentにしない。
  • Currentは同時に1Versionのみ。
  • Publishedしただけでは自動Current化しない。
  • Current変更は07の管理画面から行う。

14. card_id

  • カード名を主キーにしない。
  • 同名でもcard_idが異なれば別カード。
  • Guessの正解判定はcard_id同士で行う。
  • アプリ内部では文字列として扱う。

57. Validation

Draft VersionをPublishedにする前に データ整合性を検証する。

少なくとも以下を検証する。

  • card_id存在。
  • Version内card_id重複なし。
  • name存在。
  • classが既知。
  • typeが1 / 2 / 3。
  • rarityが既知。
  • 必要なcard_set Mappingが正常。
  • costが0以上の整数。
  • Followerのatk / life存在。
  • is_tokenが正常なBoolean。
  • tribe_modeがnormal / all。
  • card_tribes参照整合。
  • card_keywords参照整合。
  • enabledカードのimage_ref存在。
  • 前Versionからカードが意図せず消失していない。

107. 最終方針

  1. Source Dataとゲーム用Normalized Dataを分離する。
  2. card_idをカードの正式識別子とする。
  3. data_version_idとversion_codeを明確に分離する。
  4. Source由来の意味が確認できない値を推測しない。
  5. Token判定はis_tokenを正とする。
  6. Basicは非Tokenかつcard_set_id=10000とする。
  7. 分類typeとタイプtribesを分離する。
  8. 非Followerのatk / lifeはNULLとする。
  9. 能力テキストとKeywordを分離する。
  10. 画像BinaryをD1へ保存しない。
  11. Data Versionは完全Snapshotとする。
  12. Published Versionを書き換えない。
  13. 進行中ゲームのdata_version_idを途中変更しない。
  14. Version別Search Indexを使用する。
  15. Daily問題とDaily提供状態を分離する。
  16. 運営設定・監査ログをカードマスターと分離する。
  17. ゲームの一時状態をD1へ永続戦績として蓄積しない。
  18. Source Archiveを一般ゲームから直接参照しない。
