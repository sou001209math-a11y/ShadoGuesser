Shado Guesser 基本設計書

05-06：レスポンシブ

本設計書では、 Shado GuesserをPC・タブレット・スマートフォンから利用する際の 画面幅への対応方針を定義する。

単純にPC画面を縮小するのではなく、 カード検索・回答・判定確認というゲームの基本操作を、 利用可能な表示幅に応じて適切に表示する。

1. 目的

Shado Guesserは初期版では 独立したWebアプリ として動作する。

将来WordPress等の外部サイトへ組み込まれる場合も想定し、 画面そのものの幅だけではなく、 Shado Guesserが配置された 親コンテンツ領域の横幅 へ自然に追従できる構造とする。

レスポンシブ基本方針
  • PC・タブレット・スマートフォンに対応する。
  • ゲーム本体は親要素の横幅を超えない。
  • 基本的に横スクロールを発生させない。
  • 操作方法を端末によって大きく変更しない。
  • 情報の並び順を端末によって大きく変更しない。
  • スマートフォンでもカード判定を比較しやすい構造を維持する。
  • 独立Webアプリと外部サイト組み込み時で同一基本UIを使用する。

2. 対応端末

端末 対応 主な操作
デスクトップPC 対応 マウス・キーボード
ノートPC 対応 マウス・タッチパッド・キーボード
タブレット 対応 タッチ操作
スマートフォン 対応 タッチ操作・ソフトウェアキーボード

3. 横幅の基本目安

区分 目安
PC 1024px以上
タブレット 768px～1023px程度
スマートフォン 767px以下
狭いスマートフォン 374px以下も追加確認対象

これらの値は端末種類を厳密に判定するための値ではない。

実際には Shado Guesserが使用できるコンテンツ幅 を基準としてCSSを調整する。

4. ゲームRoot

Shado GuesserのUIは #sg-app 内部へ配置する。 

<div id="sg-app">

    Shado Guesser

</div>
  • #sg-app は親要素を超えない。
  • ゲーム用Classは sg- prefixを使用する。
  • 外部サイトのBody幅へ直接依存しない。

5. ゲーム本体の横幅

  • width:100% を基本とする。
  • 必要に応じて max-width を設定する。
  • box-sizing:border-box を使用する。
  • 親要素を超える固定Pixel幅を使用しない。
  • PCでは中央配置可能とする。

18. 履歴Header

履歴Headerには 開閉Icon・カード画像・カード名を表示する。

PC・Tablet・Smartphoneすべてで 同じ基本構造を使用する。

19. カード画像

  • 80px幅を基本とする。
  • 高さは自動計算。
  • 縦横比維持。
  • Smartphoneでも画像を原則表示する。
  • 閉じた履歴でも画像を表示する。

20. カード名

カード名は画像横の残り横幅を利用する。

  • 太字。
  • 最大2行を基本とする。
  • 自然な折り返し。
  • 手動改行位置をカードデータへ持たせない。
  • 可読性を損なうほど文字を縮小しない。

23. 入力欄

  • Smartphoneでは利用可能幅を最大限使用。
  • width:100% を基本。
  • 親要素を超えない。
  • 文字入力でページ横スクロールを発生させない。
  • タップしやすい高さを確保する。

24. Software Keyboard

SmartphoneでSoftware Keyboardが表示されても、 入力欄・Suggestionを利用できる構造とする。

OS・BrowserごとにKeyboard高さが異なるため、 固定Keyboard高さを前提にレイアウトしない。

  • 指で操作可能な十分な領域を確保。
  • 文字を切らない。
  • 画面幅を超えない。
  • Submitting中のdisabled状態を視覚的に区別する。

28. タッチ操作領域

  • 履歴Header全体をTap対象。
  • Suggestion候補行全体をTap対象。
  • 回答Button全体をTap対象。
  • Hint / Surrender / Exit等はButton全体をTap対象。
  • 小さなIconや文字だけを唯一のTap対象にしない。

30. 履歴の縦方向拡張

  • Keywordを省略しない。
  • 展開内容を固定高さへ押し込まない。
  • ページ全体の通常縦Scrollを利用する。

  • 自然に折り返す。
  • 固定高さなし。
  • 能力領域だけの内部Scrollなし。

34. Battle Timer

  • Serverから受け取ったdeadlineを基準とする。
  • 表示CountdownはBrowserで更新する。
  • 毎秒Serverへ問い合わせない。
  • 正式なTimeout判定はServer側。

Responsive表示によってTimerの意味・120秒ルールを変更しない。

35. Modal

  • 画面幅へ追従。
  • 左右に最低限の余白。
  • 固定幅ではみ出さない。
  • 長い内容は縦方向へ伸ばす。
  • 操作ButtonをTapしやすくする。

具体的なModal仕様は05-08を正とする。

36. Modal表示中のTimer

BattleでModalを開いても Server側deadlineは停止しない。

ModalのResponsive表示と ゲーム時間進行は別の責務とする。

37. Result Screen

通常Result ScreenもPC・Smartphoneで 同じ情報構造を基本とする。

  • 正解Cardを読みやすく表示。
  • 回答数等を狭い幅では縦方向へ配置可能。
  • Solo/Dailyでは使用Hint情報を表示可能。
  • Battleでは勝敗情報を表示。
  • 横Scrollを基本的に使用しない。

38. Daily停止画面

Daily停止専用画面も PC・Tablet・Smartphoneすべてで 利用可能な幅へ収める。 

本日はカード更新もしくは不具合の影響で
デイリーは停止されています。
またAM5:00以降に遊びに来てください。

Daily停止を 画面幅によって通常Result Screenへ置換しない。

39. Error画面

  • Error ID等が画面外へはみ出さない。
  • 問い合わせLinkをTap可能。
  • 長い内部文字列を不用意に表示しない。
  • PC・Smartphoneで同じ安全情報を表示する。

40. 横Scroll

Shado Guesserの通常ゲームUIでは 横Scrollを基本的に発生させない。

対象：
  • ゲーム本体。
  • 入力欄。
  • Suggestion。
  • 履歴Card。
  • Card詳細。
  • Ability Text。
  • Result Screen。
  • Modal。
  • Daily停止画面。
  • Error画面。

41. box-sizing

#sg-app,
#sg-app *{
    box-sizing:border-box;
}

サイト全体へ無条件に 

*{
    box-sizing:border-box;
}

を適用するのではなく、 Shado GuesserのRoot内部へ限定する。

42. 外側サイトとの余白

将来外部サイトへ組み込む場合、 外側サイトですでに左右Paddingが設定されている可能性がある。

  • 外側余白を過剰に追加しない。
  • Host側の余白との二重化を確認する。
  • ゲーム内部Cardには必要なPaddingを持たせる。
  • Hostの外側余白とゲーム内部余白を分離する。

43. PC最大幅

大型Displayでゲームが横へ広がりすぎないよう、 適切な max-width を設定できる構造とする。

44. Font Size

  • 全要素を一律縮小しない。
  • 本文はSmartphoneでも読めるSizeを維持。
  • Detail LabelはValueより小さくしてよい。
  • Card Nameの可読性を優先。
  • 数値判定を一目で確認できるSize。
  • ▲・▼を小さくしすぎない。

45. 狭い画面での調整順

要素が収まりにくい場合は、 基本的に以下の順で調整する。

  1. 外側余白を調整。
  2. 内部Paddingを調整。
  3. Gapを調整。
  4. Label文字Sizeを若干調整。
  5. Value文字Sizeを必要最小限調整。
  6. 長い文字列を折り返す。

最初から列構成を崩したり、 文字を極端に小さくする方法を選ばない。

46. 狭いSmartphone

  • 374px以下も確認する。
  • 画面外へはみ出さない。
  • 80px Card Imageを基本として調整。
  • 数値3列を維持することを優先。
  • 2列領域も可能な限り維持。
  • 長文は折り返す。

極端に狭い環境で 「最大2行のCard Name」と「十分な文字Size」を同時に維持できない場合は、 文字を読めないSizeまで縮小するより 可読性を優先する。

47. 画像読み込み失敗時

Card Imageが読み込めない場合も Header全体のLayoutを大きく崩さない。

  • 画像領域の基本幅を維持可能な構造。
  • Card Nameを確認可能。
  • 壊れた画像で横幅が拡大しない。

画像参照自体のData異常処理は04・05-04を正とする。

48. 端末回転

  • Portrait専用固定幅を使わない。
  • Landscapeへ回転した場合も新しい幅へ追従。
  • 画面回転だけでGame StateをResetしない。
  • Server Sessionを作り直さない。

49. Reloadとは別

画面回転やResizeは ページ再読み込み・Game Restartとは別操作である。 

Resize / Orientation Change

↓

Layout再計算

↓

Game State維持

50. JavaScriptで端末判定しすぎない

  • Responsive LayoutはCSSを基本とする。
  • PC専用HTML / Smartphone専用HTMLを作らない。
  • 同一DOMを再利用する。
  • JavaScriptはGame State・UI State管理を中心とする。
  • 「iPhoneだからこのHTML」等を基本設計にしない。

    flex:1 1 auto;
    min-width:0;
}

max-width:900px は実装例であり確定値ではない。

52. Smartphone CSS例

@media (max-width:767px){

    .sg-game{
        width:100%;
    }

    .sg-game-inner{
        padding-left:8px;
        padding-right:8px;
    }

    .sg-card-input{
        width:100%;
    }

    .sg-detail-field{
        min-width:0;
    }

}

Smartphone Media Queryだからという理由だけで 

grid-template-columns:1fr;

へ変更し、 2列・3列をすべて破壊しない。

53. Overflow対策

  • 画像へ適切な最大幅。
  • Flex子要素へ min-width:0。
  • Gridは minmax(0,1fr)。
  • 長文は折り返す。
  • 固定幅要素を必要最小限にする。
  • 外部Host幅を超えない。

54. Browser Zoom

PC Browserの拡大・縮小等で 実質表示幅が変化した場合も 利用可能幅へ追従する。

端末名ではなく 実際に利用可能な表示幅 を優先する。
